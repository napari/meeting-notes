### Topics

- Triage and merge PRs
    - Updating people on release process
        - Having a NAP for each release seems like a lot of overhead compared to just having an image SC thread and a docs PR for home page
        - because the image sc thread can just be edited on the fly while NAP has to have a PR and a review (even though home page would also need a PR and review)
        - Could be good to have a NAP for major releases where we list what we will include and won't include, especially for DiR works on features that they know they need to release
        - if we have a NAP for releases, we should *keep* having NAPs - people are worried that we'll have one and then never again
        - we should also use milestones a little better about what's short term and what is long term
        - Draga thinks that updating the NAP for a release feels like a huge burden because our schedule estimates are broken. We always dramatically underestimate how long it will take for an alpha to be released, and when we miss the deadline, we only bump it by like 2 days instead of a reasonable amount of time
        - Tim likes having milestones and listed "blockers" of what will get done before the release, because then even if the schedule is a little out, it's obvious what still needs to be done. We keep this for the docs, but not for the other repos
        - Peter is warming up to the idea of a NAP for this purpose, because it includes the whole organization
        - Grzegorz makes the point that rough release schedule might be really important for people working on napari from within other organizations, and people working with users, where they might need a longer lead time 
        - we should revisit this when we've spun up DiR and potentially only for the next major release
- Discuss faster docs builds for local development [Issue 625](https://github.com/napari/docs/issues/625)
    - everyone in favour of a quick no-api no-execution docs build
    - but when do we do a full build - on rtm?
    - we often break examples though
    - does circle ci support cache?
    - people in favour of a full build on ready-to-merge
    - PB: even if we skip api and code execution, it's not going to be 1 minute, it's going to be more like 5 minutes
    - - Juan thinks if we're not running code, we should be able to parallelize the build and it should be actually fast
    - Tim makes the point that even html-live (which Peter uses locally) takes forever to build the first time so it's offputting
        - especially since the viewer keeps popping up, your machine is basically unusable
    - Grzegorz recommends using `make docs` as the quick build, and then `make docs all` or whatever as the full build, because people are more likely to just run `make docs`
- Grzegorz PR updates unnamed logger to `napari` logger to appease the pre-commit rule but also because it's good practice
